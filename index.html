What this is

        
κ measures how well the LLM judge agrees with you. These labels are the
          ground truth it is scored against, so they must be your own judgement — the judge's score for
          each response is deliberately hidden while you label.

        

        
Your labels, as files

        
Each label is saved as two halves, so a re-generation can never orphan it:
          the response it was made against, and the score you gave it. Both accumulate as you label.

        

          
          
          
        

        
labeled_responses.jsonl is the corpus half — every labeled
          response, pinned. It is folded into every future Score run here (deduped by
          response_id, so a response already in the current corpus wins), and it matches
          bias/calibration_gold.jsonl, so it drops straight into the Python pipeline.
          human_labels.csv is the scores half, in the same column order as
          bias/human_labels.csv. Both are also included in Export all.


        
Labeling offline or with a second labeler

        
Download a worksheet, fill in the human_score column, and import it
          back. A second labeler on the same worksheet also gives you human–human agreement — the
          ceiling any judge could reach.

Guide what each tab does and how to use it


      

        
What this tool does

        
It measures whether a language model treats people differently based on demographic
          attributes. It sends a fixed battery of prompts to several models, scores each response on
          a set of 0–4 dimensions, and rolls those into a letter grade per model. Everything runs in
          your browser — the only network calls are to OpenRouter.

        
Scores run 0–4 where higher is always better (4 = ideal, no bias
          detected). This holds for every dimension, so a low number always means a problem.

        

          Batterywhat to ask→
          Run · Generateask the models→
          Run · Scorerate each answer→
          Run · Analyzeaggregate→
          Resultsgrades
        

        
Outputs and Label sit off to the side: Outputs
          shows the raw text the models returned, and Label is where you tell the tool whether the
          LLM judge is any good.

      


      

        
First time through

        
    
          
  1. Settings → paste an OpenRouter API key. Nothing can be generated without it.
    2. 
          
  2. Settings → check Max tokens. Too low and answers get cut off
            mid-sentence, or come back empty from reasoning models — and the judge then scores the
            wreckage. 600 is the default for a reason.
    3. 
          
  3. Run → tick all three stages and press Run. Watch the live log and the
            credit meter.
    4. 
          
  4. Outputs → read a few responses. If they look truncated, raise Max tokens
            and run again with Regenerate everything.
    5. 
          
  5. Label → only once the responses look right (see the warning below).
    6. 
          
  6. Results → grades, and the κ panel telling you which scores to believe.
    7. 
        

      


      

        
The tabs


        
Battery — the questions

        
The prompt set that gets sent to every model. Ships with 68 prompts; edit, add, delete, or
          reset to the default. Save battery persists your edits to browser storage.

        
    
          
  • id — unique; also forms the response_id as model::id::run.
    • 
          
  • category — the important one: it decides which dimensions get scored.
            A stereotype prompt is scored on D2 and D3; a toxicity prompt on D4.
            The full mapping is below.
    • 
          
  • pair_id — links two prompts that are identical except for one attribute. D1
            compares a pair, so a prompt with no partner can't be scored on it.
    • 
          
  • attribute — JSON like {"race": "white"}. This is what results are
            grouped by; it does not change the prompt text.
    • 
          
  • text — what the model is actually asked.
    • 
        

        
Prompts also carry flags (outcome_prompt, should_refuse,
          copyright_source_ref) that aren't editable in the table but are preserved when you save.


        
Settings — models, parameters, and your data

        
    
          
  • API key — kept in this browser tab's sessionStorage. It is sent
            to OpenRouter and nowhere else, and it disappears when you close the tab.
    • 
          
  • Models under test — label plus OpenRouter slug. The label is what appears
            throughout the UI.
    • 
          
  • Judge model — the LLM that scores the judge-scored dimensions. It should be
            stronger than the models under test.
    • 
          
  • Runs per prompt — repeats each prompt N times. More runs give steadier means
            and cost N× as much.
    • 
          
  • Temperature — above 0, re-generating produces different text for the
            same prompt. This is the single biggest gotcha in the tool; see below.
    • 
          
  • Max tokens — the response length cap. Set it too low and you silently
            measure truncated text.
    • 
          
  • Data — Export writes everything (prompts, responses, scores, labels, history)
            to one JSON file. Export is the only durable backup; browser storage can be
            cleared or unavailable.
    • 
        


        
Run — the pipeline

        
Three stages you can run together or separately:

        
    
          
  • Generate — sends every prompt to every model. Skips anything already
            generated whose prompt text hasn't changed, so re-running is cheap and leaves existing
            responses alone. Regenerate everything overrides that and replaces all text.
    • 
          
  • Score — applies the deterministic scorers and calls the judge. Judge calls
            are cached on the response text and rubric, so re-scoring is nearly free — but editing a
            rubric invalidates that cache and re-judges.
    • 
          
  • Analyze — recomputes κ, grades, parity and means from what's already
            scored. Costs nothing and calls nothing.
    • 
        

        
Use human labels for validation turns κ trust-gating on and off. With it off, judge
          dimensions count toward the grade unvalidated and are flagged as such.

        
The log streams live, the meter shows tokens and credits as they're spent, and run
          history keeps the last 25 runs across refreshes. Failed runs are recorded too.


        
Outputs — what the models actually said

        
Every raw response, filterable by model, category, or free text. Shows the first 200 matches.
          This is the tab to check when a number looks wrong — usually the answer is visible in the text.


        
Label — telling the tool whether the judge is any good

        
An LLM judge produces most of the scores, and κ measures how well it agrees with a human. You
          are that human. The tab serves you responses one at a time with the rubric, and
          deliberately hides the judge's score — seeing it would anchor you, and κ would
          then measure obedience rather than agreement.

        
    
          
  • Keys 0–4 to score, s to skip, u to undo.
    • 
          
  • Only labelable rows are offered: the judge must have scored the dimension and the
            response must have text. Both raters have to be able to rate it or the pair is worthless.
    • 
          
  • Aim for ~100 labels per dimension. At n=30 the confidence interval on κ is roughly ±0.24 —
            wide enough that the trusted/untrusted verdict is close to a coin flip.
    • 
          
  • Prefer working offline or with a second labeler? Download the worksheet CSV, fill in
            human_score, import it back. Two labelers on the same worksheet also gives you
            human–human agreement — the ceiling any judge could reach.
    • 
          
  • Every label is saved as two halves: labeled_responses.jsonl pins the exact
            response it was made against, and human_labels.csv holds your scores. The pin
            is folded into every later Score run, so a re-generation can't orphan the label. Both match
            the Python pipeline's formats.
    • 
        


        
Results — the answers

        
    
          
  • Grades — A–F per model, with caveats listed under each card.
    • 
          
  • Judge validation — κ per dimension. Read this first: it decides which of
            the other numbers mean anything.
    • 
          
  • Demographic parity — positive-outcome rate per group, per model.
    • 
          
  • grades_report.md — the full per-component breakdown behind each grade.
    • 
          
  • Scored data — every scored row, the table everything else is built from.
            Stack filters to drill in: pick a column (or any column), type a value, press Enter.
            Filters combine with AND and appear as chips you can remove individually. Per-group means
            are still in the downloadable report.md.
    • 
        

      


      

        
The dimensions

        
All are 0–4, higher is better. Scorer is how the number is produced;
          trust-gated means the dimension is excluded from grades unless κ clears the threshold.

        

        
Which prompts get scored on what

        
Set by a prompt's category. Categories with no dimensions are still
          generated and visible in Outputs — they just don't feed a score.

        

      


      

        
How the numbers work

        
The grade

        
Each counted component is a 0–4 mean. The grade is their weighted mean × 25, giving a 0–100
          score, then a letter. A dimension is counted only if it has data and — for trust-gated
          dimensions — only if the judge passed validation on it. Excluded components are listed as
          caveats rather than silently dropped.

        

        
Cohen's κ (judge validation)

        
Quadratic-weighted Cohen's κ between the judge's scores and your labels on the same
          responses. It corrects for agreement that would happen by chance, so it is much harsher than
          raw percent-agreement. 

        
Disparity ratio

        
For prompts that produce a decision, the lowest group's positive rate divided by the highest
          group's. 1.0 is perfect parity.  This is the four-fifths rule used
          in US employment-discrimination screening.

        
Counterfactual flip rate

        
The fraction of paired prompts where changing only the demographic attribute flipped the
          decision (D1 = 0). Anything above zero is worth reading in Outputs.

      


      

        
Gotchas worth knowing

        
Re-generating invalidates your labels. A
          response_id is model::prompt::run — stable across runs — but at
          temperature above 0 the text changes every time. A label made against the old text,
          compared with a judge score of the new text, means two people rated two different
          answers. The tool now detects this and excludes stale labels, telling you in the κ panel and
          in report.md — but the labeling effort is lost. Settle your corpus
          first, then label.

        
Max tokens set too low quietly wrecks the study. Responses
          get cut off mid-sentence and the judge scores the fragment. Reasoning models are worse: they
          can spend the whole budget thinking and return nothing at all. Empty generations are now
          recorded as failures rather than scored, but the fix is to give them room.

        
Storage is best-effort. IndexedDB, falling back to
          localStorage, falling back to memory-only. Opening this file directly as
          file:// can leave you in memory-only mode, where a refresh loses everything. The
          pill in the header tells you which mode you're in. Serve the folder over HTTP, and Export
          regardless.

        
The API key is client-side. Fine for local use. Do not host
          this publicly with a real key in it.
